## 0. 摘要

两个问题彼此独立、可分开发布，但都落在「一条会话同一时刻只应有一个在途状态机」这条主线上：

- **问题一**：daemon 对外下发的思考块是「累积全文快照」，而 ACP 协议同 `messageId` 的 chunk 是「追加」语义，导致客户端把同一段文本反复追加（O(n²)），表现为推理重复输出乃至看似死循环。根因在**语义边界不匹配**，不在模型。
- **问题二**：daemon 在会话仍处于 `Running` 时收到新输入，会**静默丢弃在途状态机**并启动第二个 agent loop——既不取消也不等待旧循环，旧循环随后还会反向破坏新循环的收尾与取消能力。

推荐方案（**两项均已拍板**）：

- **问题一：B3（已拍板，不带语义标记）**。在 core 的事件层产出**真增量**、内部仍保留完整块；`ThinkingBlock.thinking` 的语义由「累积全文」**直接改为「增量」**并写入 proto 注释，**不新增标记字段**（变体 C 评估后未采用，见 §3.5）。O(n²) 在总线层即被消除；provider、持久化与签名回传语义零改动（见 §3.6、§4）。
- **问题二：拒绝式（已拍板）**。核心不变式：**同一会话绝不允许出现第二个并发 agent loop**。做法是在**用户输入受理路径**上以「是否存在在途循环取消令牌」为判据**拒绝**（G1），并移除全部静默重置旁路（G3）；纵深为 ACP 侧终态确认与兜底取消（G4，可选）。**不采用**世代/归属校验与「启动即取代」（见 §6.3 的前置条件说明）。

两项修复建议实施顺序：**先问题二，后问题一**（见 §11）。

## 1. 背景与问题定义

### 1.1 术语

- **快照（snapshot）语义**：每一帧携带「截至目前的完整文本」，消费方应**覆盖**渲染。
- **增量（delta）语义**：每一帧只携带「自上一帧以来新增的文本」，消费方应**追加**渲染。
- **思考块（thinking block）**：模型推理过程文本；Anthropic 还会附带签名（signature），用于把思考块作为有效历史回传。
- **在途状态机（in-flight loop）**：`start_loop` 与 `finish_loop` 之间存活的 agent 循环。

### 1.2 问题一：thinking 流式语义缺陷

已被 ACP 侧观察到：Zed 中思考文本被反复追加、长度呈平方级膨胀，观感像「推理死循环 / 重复输出」。TUI 未见同类问题。核对结论：**纯语义不匹配**——生产端说「这是全文」，消费端理解为「这是新增片段」。

证据锚点（已核实）：

- 生产端 openai 兼容路径：每收到一个推理增量就把**累积后的全文**作为思考块发射（`crates/visp-llm/src/openai.rs:873-881`）。
- 生产端 Anthropic 路径：同样以累积全文发射，并附带当前签名（`crates/visp-llm/src/anthropic.rs:1128-1153`）；`BlockStop` 处另有一条「发射最终完整块」的分支（`anthropic.rs:1175-1185`）。
- 内部事件与装配：`ChatEvent::ThinkingBlock`（`crates/visp-core/src/provider.rs:161-172`）→ core 收集进 `StreamOutput.thinking_blocks`（`agent_loop.rs:404-415`）→ 转发 `AgentEvent::ThinkingBlock`（`agent_loop.rs:499-506`）→ 装配进 `extra_blocks`（`agent_loop.rs:668-672 / 797-822 / 825-847 / 849-856`）。
- daemon 原样透传全文与签名（`crates/visp-daemon/src/service.rs:1828-1843`）→ proto（`visp.proto:195-202`，无增量字段）。
- ACP 侧对同一 `messageId` 追加（`crates/visp-acp/src/translate.rs:89-97`）→ 与快照语义冲突，形成 O(n²)。
- TUI 为**覆盖**语义（`crates/visp-tui/src/app.rs:580-589`），故仅表现为「不坏」，并非「正确」。

### 1.3 问题二：daemon 双 agent loop

daemon 在**主会话仍有在途循环时**收到新的用户输入，会**静默把状态改回 `Idle` 并启动第二个 agent 循环**——既不取消、也不等待旧循环；旧循环此后无人可取消，并会在自然收尾时反向改写新循环的状态与取消令牌。

**可达性需精确界定**：TUI 在正常流式期间是封锁输入的（`event.rs:894-896`），因此该情形**不出现在正常使用路径**，仅出现在**收尾窗口**——即客户端已提前放开输入门禁或已提前结束本轮，而 daemon 侧循环仍在运行（TUI 取消、断线重连、ACP 兜底收尾与流断开、以及任何直连 gRPC 客户端）。完整触发矩阵见 §5.2。

本期定为**拒绝式修复**：在用户输入受理关卡以「是否存在在途循环取消令牌」为判据拒绝，并移除全部静默重置旁路（见 §5、§6）。

### 1.4 设计由来：快照语义是「流式显示」的副产物，不是被论证过的契约

这一节回答「现状为什么是快照」，并据此界定**哪些既有行为需要保留、哪些只是历史偶然**。结论先行：快照**不是**原始设计，也**没有任何文档论证过**；它是 2026-06-13 一次流式显示改造的副产物。

时间线（git 实证）：

| 时点 | 提交 | 语义 |
|---|---|---|
| 2026-06-05 | `c6850a740` | **最初：一轮响应一个完整思考块**。Anthropic 缓冲到内容块结束才发射一次；既非快照，也非增量。 |
| 2026-06-11 | `f30254c8` | OpenAI 侧同样**单块**：缓冲到首个正文增量或流结束才发射一次。 |
| 2026-06-13 | `b9a571c8`（openai）、`8c610466`（anthropic） | **改为「逐片累计全文」**——现状的来源。提交标题即 `stream reasoning/thinking content character-by-character`。 |

`b9a571c8` 的提交说明记录了三条**联动**改动，其动机只有「逐字流式显示」一条：

1. **provider**：每收到一个推理增量就**立即发射一帧**（原注释：「立即发射 ThinkingBlock 实现流式显示（不等待 text delta）」）。
2. **core**：改为「只保留最新块」（提交说明给出的理由是 `to prevent context window bloat from streaming increments`，即防止逐片累积撑爆上下文）。
3. **TUI**：新增「原地覆盖最后一行」的渲染方式（提交说明：`in-place instead of appending new lines`）。

**「发全文而非增量」是第 1 条与第 3 条组合的必然结果**：既然每片都发、而消费方是**覆盖**，则每片必须是全文，否则覆盖后只剩最后一小片。因此快照是副产物，未曾作为契约被论证。

需要更正的常见误判：「必须携带完整文本 + 签名才能回传」是**今天的硬约束（§2.4）**，不是当初改成快照的动机——原始 Anthropic 实现确实缓冲到内容块结束才发射，但提交说明**未以签名保真为由**；且原始设计阶段没有任何设计文档讨论过快照与增量的取舍（`docs/design/visp-design-block-abstraction.md` 讨论的是渲染层样式抽象，与思考语义无关）。

**对本设计的含义（三条）**：

1. **根因是事件模型自身的语义不一致**：`TextDelta` 是增量，`ThinkingBlock` 却是块快照。ACP 只是第一个按协议契约（同 `messageId` 追加）消费它的客户端，因此第一个暴露该缺陷。
2. **当年的改造只处理了上下文侧膨胀，未处理线协议侧膨胀**：core 用「只保留最新块」防止上下文被逐片撑大，但线协议上仍是 O(n²)；TUI 靠覆盖吸收、ACP 按追加消费才暴露。这解释了缺陷为何能潜伏两个多月。
3. **快照不应被视为「需要保留的既有契约」**：因此方案选择不必以「保持快照协议」为前提，而应优先与既有的**增量模型（`TextDelta`）对齐**；且**思考块边界只在 provider 侧可精确得知**（每轮 LLM 响应一个累积器），这是「在边界处猜前缀」（B2）与「在源头产出增量」（B1/B3）区别的根本原因。
4. **TUI 改造的体验成本可降级**：把 TUI 由「赋值覆盖」改为「向同一行追加后缀」，其渲染结果与原地覆盖**视觉等价**（仍是原地流式），UX 零变化；真正的成本只在实现与测试断言上。

## 3. 问题一：方案对比

### 3.1 方案总表

| 方案 | 增量产生位置 | 触及范围 | 消除 O(n²) 的边界 | 持久化/签名 | 主要风险 |
|---|---|---|---|---|---|
| **A** | ACP 适配层 | 仅 ACP | 仅 Zed 末跳 | 不涉及 | 只修一个客户端；daemon↔客户端与 TUI 仍吃平方级流量 |
| **B1** | provider（真增量）+ core 组装 | llm + core + tui + proto + 测试 | 总线及全部客户端 | 需重构组装与签名/多块逻辑 | 最高；provider 快照测试全改；回传语义受牵连 |
| **B2** | daemon 与客户端交界 | daemon + tui + proto | daemon 内部总线仍 O(n²)，仅客户端末跳消除 | 不涉及 | 每连接×每会话差量状态；块边界启发式；滞后/重连一致性 |
| **B3** | **core 事件层**（核心内部保留完整块） | core + daemon（映射）+ tui + proto + 测试 | **总线及全部客户端** | **不涉及（完整块原样保留）** | 新增事件变体；AgentEvent 语义显式化 |

### 3.2 方案 A（用户已否决，仅对照）

只在 ACP 适配层把快照换算为增量。零侵入，但只修 Zed；daemon→客户端的平方级链路、daemon 内部总线与 TUI 流量均保留。**否决**。

### 3.3 方案 B2（备选）——独立可行性评估

**可行性：可行。** daemon 每个 Chat 连接都有独立的出站转发任务（总线订阅 + 逐帧转换），差量状态天然可挂在「每连接」作用域：随连接建立而创建、随连接断开而销毁，不跨客户端泄漏。转换点唯一（`service.rs:1366-1440` 的出站转发任务调用 `service.rs:1828-1843` 的映射），落点清晰。

需要处理的关键问题：

1. **状态键（多会话）**：出站任务转发该连接可见的**全部** session 帧（主 agent 与子 agent 混流），并非只转发目标 session。因此差量状态必须**按 session 维度分别维护**，不能用「单条上一条」。
2. **块边界判定**：帧只携带快照文本，不携带块标识/序号。只能以「新快照是否以前一快照为前缀」推断「同块续传 vs 新块起始」。该启发式在跨 LLM 调用、跨块时可工作，但存在极小概率误判（新块文本恰好以前块全文为前缀），后果仅为一次性多显示。
3. **断流/重连一致性**：连接断开→差量状态销毁，无残留；但**重连回放路径本就不下发思考帧**（`service.rs:1639-1729`），故重连后思考内容本就不回放。差量语义不会使其更差，但也不会引入自愈。
4. **滞后（Lagged）自愈退化**：快照语义下丢帧后下一帧全文可「自我修复」；改为增量后，丢失的增量**永久缺失**。总线滞后重放目前只重建文本/工具历史、不含思考。这是**所有增量方案的共有代价**（B1/B2/B3 都如此），必须在文档中显式声明。注：该自愈窗口**只存在于同一连接内的后续帧**；一旦走 Lagged replay 或重连（回放本就不含思考帧），快照与增量都不回放思考，故新方案实际减少的可见窗口有限。
5. **静默改语义**：字段语义由快照变为增量属**破坏性变更**；本设计已决议**不加标记**（§3.5），改以 proto 注释显式写明，并接受旧客户端静默降级。

**结论**：B2 可行，但代价是「每连接 × 每会话的有状态差量器 + 块边界启发式 + daemon 内部总线仍为 O(n²)」；且仅把差量搬到 daemon 边界**并不能省掉 TUI 的修改**（同一线协议下 TUI 也必须改为追加），因此它相对 B1 的「最干净」优势被削弱。

### 3.4 方案 B3（已选定）

**做法**：provider → core 的内部契约**保持快照不变**（`ChatEvent::ThinkingBlock` 不动，provider 与其快照测试零改动）；在 core 的流收集阶段**同时**做两件事——把「本轮完整块」继续累积进既有向量（供持久化、历史回传、速率估算），把「相对上一帧的增量」作为**新增的显式下游事件**发射。

**为何优于 B2**：

1. **状态生命周期精确**：core 的流收集函数每次调用恰对应「一轮 LLM 响应」，增量基线在这一轮内维护、函数返回即自然丢弃。B2 的差量器则跨连接、跨会话、跨轮长期存活，需要更复杂的键管理与清理。
2. **无需跨连接猜边界**：core 清楚「新一轮」的确切起点；B2 只能靠文本前缀启发式。
3. **O(n²) 消除到总线层**：B3 使 daemon 内部显示面总线携带的也是增量（总字节降为 O(n)）；B2 仅在客户端末跳去重，总线仍为 O(n²)。
4. **持久化/签名/回传语义完全不动**：满足 §2.4 的硬约束，且**不触碰 `agent_loop.rs:499-506 / 825-847` 这两个既有缺陷**（可另立项，见 §9）。

**代价**：`AgentEvent` 需新增一个「思考增量」事件变体（语义显式，不复用快照事件）；daemon 需把该变体映射为 proto 思考块帧；TUI 需由覆盖改为追加。

### 3.5 变体 C：显式语义标记（评估后未采用）

曾评估两种「为思考块消息新增显式语义标记」的落地形态，用以让「快照 vs 增量」在协议层自描述、并支持消费方对未知值保守回退：

- **C1（附加字段，默认=快照）**：新增一个语义标记（布尔或枚举）。线级向后兼容（未知字段被忽略），消费方按标记选择覆盖或追加。
- **C2（新增 oneof 变体）**：语义最干净，但旧客户端会整体丢弃未知变体（思考不显示），且需要能力协商。

**结论：不采用。** 本仓库的生产者（daemon）与两个消费方（TUI、ACP）**同仓同批发布**，不存在需要跨版本协商的外部消费方；此时新增标记字段会引入一层消费方分流、并牵动所有字面构造点，其收益主要是「契约自描述」，不足以抵偿机制成本。

**明确接受的代价（须写入交付说明）**：

- 这是对共享契约的**静默语义变更**——字段名与类型不变，仅含义由「累积全文」变为「增量」；
- 消费方**没有可编程信号**判断自己是否理解正确；**若出现混合版本本地部署**（如手动用旧 `visp-tui` 连新 daemon），旧 TUI 会静默降级为只显示最后一片，而不是可诊断的报错。在「三二进制同批构建 + 本地回环连接」的常规拓扑下，该情形近乎不出现；
- 失去「对未知标记保守回退」与「未来语义扩展位」两项能力。

**缓解措施**：在 proto 注释中显式写明 `thinking` 为增量语义（见 §4.3），并在注释中指向「语义契约回归测试」（core 侧「连续同块快照 → 只发增量」与「流式期间不产生快照变体」两条用例）；发布说明中点明该契约变更；后续若出现跨版本消费方或第三种语义需求，再评估引入标记。

### 3.6 结论（问题一）：B3（已拍板，不带语义标记）

**选定：B3（core 事件层产出真增量，内部保留完整块），且不为 proto 新增语义标记**。理由：

1. **消除范围最彻底**：O(n²) 在**总线层**即被消除，全部客户端（含 TUI）与 daemon 内部显示面总线均受益；B2 只消除客户端末跳，内部总线仍为 O(n²)。
2. **状态生命周期精确**：增量基线以「一轮 LLM 响应」为界，随该轮结束自然丢弃；B2 的差量器需跨连接、跨会话、跨轮长期存活并管理键与清理。
3. **无需猜块边界**：块边界只在 provider 侧可精确得知（每轮一个累积器）；B2 只能用「前缀启发式」推断，存在误判。
4. **零触及持久化与签名语义**：provider、`extra_blocks` 装配、历史回传路径全部不变，满足 §2.4 的硬约束。

代价与取舍：

- 新增一个**显式的「思考增量」事件变体**（不复用快照事件，语义自描述）；
- TUI 由「赋值覆盖」改为「向同一行追加后缀」——与现状**视觉等价**（§1.4 含义 4），成本只在实现与测试断言；
- **不改 proto 字段**：`ThinkingBlock.thinking` 的语义直接由「累积全文」改为「增量」，仅更新注释（§3.5 已记录该选择的代价与缓解：静默语义变更、旧客户端静默降级、失去回退与扩展位）。

**未采用的候选（留档）**：B2（在 daemon 边界增量化，core 完全不碰，但代价见 §3.3）；B1（改动面最大，牵连回传语义）；A（仅修 Zed，已否决）；C（为协议新增显式语义标记，见 §3.5）。

## 4. 问题一：方案（B3）设计要点

只描述职责、流程与边界，不含实现细节。

### 4.1 模块职责划分

| 模块 | 职责（改动后） |
|---|---|
| provider（llm） | **不变**。继续以「累积全文快照」上报思考块（内部契约保持快照）。 |
| core 流收集 | 接收快照序列；维护「本轮完整块」用于内部装配；向外产出**真增量**（相对上一帧的新增部分）。每轮响应开始时重置基线。 |
| core 装配/持久化 | **不变**。仍以「本轮完整块」装配 `extra_blocks` 并落库，保证历史回传与签名完整。 |
| daemon | 把「思考增量」事件映射为 proto 思考块帧（`thinking` 即增量文本、`signature` 为空）。 |
| proto | **仅更新注释**：`thinking` 字段语义改为「增量」（无字段变更，见 §3.5）。 |
| TUI | 思考渲染由「覆盖」改为「追加」；同一思考消息内的多次增量累积到同一行。 |
| ACP | **不需改**：同一 `messageId` 追加消费方式天然适用于增量。 |

### 4.2 增量产生的规范（输入/输出规范）

- **输入**：本轮 LLM 响应内，按到达顺序的思考块快照序列（每帧为「截至目前完整文本」，可能带签名）。
- **输出（对外）**：增量序列——每帧只含「相对同块上一帧的新增文本」。拼接全部增量应恒等于该块最终完整文本。
- **基线规则**：
  - 同一块内，新快照以前一快照为前缀 → 增量为差集尾部。
  - 新快照不以前一快照为前缀（新块 / 新一轮 / 内容跳变）→ 视为新块起点，本帧增量 = 该帧全文，并重置基线。
  - 增量为空的帧不向下游发射（例如带签名但文本未变的终帧）。
- **完整性保证**：无论对外如何增量，内部「本轮完整块」向量与当前装配逻辑保持原有语义，**不得**因增量改造而丢失完整文本或签名。
- **发射点唯一性**：流式路径**只**发射增量变体，**不得**再发射快照变体——两者映射为同一 proto 帧类型，若同时出现，消费方会把快照当增量再追加一次，结果比现状更差。当前仓库**不存在非流式思考生产者**，故旧快照变体与其映射仅作为兼容既有匹配臂而保留；确认无其他路径后应随后删除（避免成为无生产者的死变体）。

### 4.3 语义契约的表述方式（无标记字段）

- `ThinkingBlock.thinking` 的语义**直接**由「累积全文快照」改为「增量」，**不新增标记字段**（决议与代价见 §3.5）。
- 契约靠 **proto 注释显式写明**来防止再次误解——本次根因正是契约语义未被写明（见 §1.4）。实现侧统一以「消费方追加」为准。
- 由于没有标记，消费方**无法**对「语义版本错配」做程序化回退；这是本选择已接受的代价。

### 4.4 边界情况

- **多思考块**（Anthropic 交错思考/工具）：按「非前缀即新块」切分；core 内部只有最后一块的既有行为**本期不改**（见 §9）。
- **思考 + 工具、无正文**：装配分支仍会丢签名的既有缺陷**本期不改**，但**本方案不使其恶化**（对外只发增量，回传仍走既有路径）。
- **仅思考无正文**：core 现有「继续循环」的判定基于完整块向量，不受增量改造影响。
- **重复/回退内容**：若某帧快照短于上一帧（异常），按「非前缀」处理为新块起点。
- **回退时的显示残留（已知差异，本期接受）**：上一条的异常回退场景下，core 会发该帧**全文**，而 TUI/ACP 按「追加」消费 → 行内变成 `ABC + AB`（旧文本残留、看似重复）；落库 `extra_blocks` 仍只保留最后一块 `AB`。即**显示多于持久化**，属显示层问题（本轮如实记录，未加显示层回写逻辑）。
- **前缀碰撞导致块合并（已知差异，本期接受）**：同一轮内若后一思考块的**首帧恰好以前一块全文为前缀**，基线 `strip_prefix` 命中 → 只发尾部 → 显示为 `ABC`（即后块全文），而非设计期望的「块1+块2」拼接 `ABABC`。「非前缀即新块」的判定无法识别该情形，同样属显示层问题。
- **多块时显示内容可能多于持久化内容（已知差异，本期接受）**：core 内部仍只保留最后一块用于 `extra_blocks`，而对外增量按块累积；一轮内出现多个思考块时，TUI/ACP 会显示「块1 + 块2」的拼接，而落库/history 仍只有最后一块。相比旧快照语义（显示也只剩最后一块），新行为**不丢显示内容**，属可接受差异，但须以用例固化。
- **跨轮追加到同一行**：thinking-only 会跨多轮；每轮基线重置、首帧为该块全文，TUI 会把它追加到上一轮仍在的同一 Thinking 行。该差异同样以用例固化（§10.1）。

## 5. 问题二：机制分析（已核实）

### 5.1 当前行为链

1. daemon 收到用户输入，主会话 `Running` → **静默**把状态重置为 `Idle`，不取消、不等待（`service.rs:617-631`）；该分支的注释把「恢复场景不应出现 Running」写成了防御性重置，**而该「静默重置」本身才是缺陷来源**。
2. orchestrator 侧对非 `Idle` 主会话再次**静默**重置后再启动（`orchestrator.rs:386-398`）。
3. 启动循环只校验状态为 `Idle`（`session.rs:347-388`）；真正的忙不变式（`SessionBusy`）存在，但被上面的静默重置绕过。
4. 收尾动作写状态 + **无条件移除**取消令牌，**不取消**（`session.rs:391-400`）。
5. 旧循环持有的取消令牌副本仍存活，此后**无人能取消**（取消动作只对仍在映射中的令牌生效，`session.rs:460-464`）。
6. 旧循环的下场：无法取消；仍通过各自转发任务向总线发帧；工具审批 120s 超时后继续；LLM 提问等待虽已可取消（`agent_loop.rs:1862-1881`）但因令牌已被移除而**无人触发**；DB 无破坏性冲突，但产生**交错重复回合**与顺序错乱（各循环持有各自的上下文快照）。
7. **二阶故障**：旧循环稍后自然收尾再次执行收尾动作，把映射中**属于新循环**的令牌移除并改写状态 → 新循环成为不可取消的孤儿。**触发路径不止「旧循环迟到」**：正常完成路径同样存在——`agent_loop` 发完 `Done` 后**立即**移除令牌并置 `Completed`，而 orchestrator 的 `handle_done` 收尾尚未执行；此窗口内到达的新输入会因「令牌已无 + 状态为终态」被放行并起新循环，随后旧 `handle_done` 踩掉新循环的令牌与状态（**不是**两个循环并存，而是旧记账孤儿化新循环）。见 §5.2 的 B6 与 §6.2 的 G5。

> 说明：第 7 条是「两个 loop 并存」才成立的衍生故障；拒绝式下第二个 loop 永不启动，故第 7 条被从根上消除（见 §6.3 的前置条件）。

### 5.2 触发条件（已更正）

**准确表述：正常运行期不会出现，仅在「收尾窗口」出现。** 触发前提是「daemon 侧循环仍在跑，但客户端已提前放开输入门禁 / 已提前结束本轮」。逐窗口如下：

| 编号 | 窗口 | 证据 | 说明 |
|---|---|---|---|
| B1a/B1b | TUI 按 Ctrl+C（确认框场景与非确认框场景） | `event.rs:684-703`（两路都在同一分支内并 `return`） | 先置「非生成」再异步发取消；取消尚未生效。注：`event.rs:797-807` 是一处**不可达的重复 Ctrl+C 分支**（既有死代码，本期不清理，仅更正锚点） |
| B1c | TUI 在生成中按 Esc 关闭确认框 | `event.rs:765-783` | 关闭确认框即为拒绝响应，并提前置「非生成」+ 发取消 |
| B2 | ACP 兜底收尾后 daemon 循环仍在跑 | `crates/visp-acp/src/agent.rs:212-228` | 10s 兜底与 Chat 流断开都会结束本轮 |
| B3 | Chat 流断开时循环仍在跑 | `agent.rs:212-216` | daemon 无断开清理 |
| B4 | 断线重连硬置「非生成」 | `crates/visp-tui/src/app.rs:412` | 重连即放开输入门禁 |
| B5 | 任何直连 gRPC 客户端 | 无门禁 | 不受 TUI / ACP 约束 |
| B6 | **正常完成路径的令牌移除时序**（三轮审核新发现） | `agent_loop` 发完 `Done` 即收尾并移除令牌；orchestrator 的 `handle_done` 收尾在**同一条 `select!`** 上、顺序不保证 | 窗口内到达的新输入：守卫因「令牌已无」放行，orchestrator 因「状态为终态」重置 → 起新循环；随后旧 `handle_done` 把新循环的令牌/状态踩掉。人手输入下极窄，直连 gRPC / 脚本化提交可达 |

补充事实：**TUI 正常流式期间输入是被封锁的**（`event.rs:894-896`），因此「生成中直接再发一条输入」在 TUI 正常路径下不可达；上表窗口的共同特征是**客户端先放开门禁、而取消/收尾是异步的**，于是门禁放开与 daemon 真正结束之间存在时间差。

### 5.3 现有关联测试

- `service.rs:3699`：显式断言「`Running` 被重置且可接受」——任何修复都会打破它，需同步改写为「拒绝」。
- `orchestrator_tests.rs:3253 / 3262`：把「重置后重开」当作正常模式；其中「同会话第二回合」属于**终态→Idle 的合法转换**，修复后必须仍然成功（见 §6.2 G3 的形态）。
- `session.rs:771-788`：收尾语义（移除但不取消）的对照；`791` 是 delete/cancel 用例，与收尾语义不同。
- **目前无任何测试覆盖真实并发双循环。**

### 5.4 关键发现：为什么选「拒绝」而不是「释放即取消 / 取代」

单看「给收尾动作补上取消」或「启动即取代」，都必须叠加**世代 + 收尾归属校验**才能避免「旧循环迟到的收尾破坏新循环」——这带来一整套二阶机制。而一旦把并发**在第一道关口就拒绝**，第二个循环永不启动，上述二阶机制及其全部配套（世代、归属校验、取代时序）随之**全部不需要**（完整论证见 §6.3）。

这是「拒绝式」相对「取代式」的结构性优势：**用一条「不产生并发」的不变式，替换掉一整套「并发下的仲裁机制」**。

### 5.5 受理边界约束（显式，防死锁）

**守卫只能加在「用户输入」这一条消息分支上（`service.rs:611-731` 的用户输入分支），绝不能加在整个入站层。** 理由：工具审批 / LLM 提问的答复走的是**另一条消息**——按 `query_id` 经 `pending_queries`（`service.rs:595`）由 `route_daemon_user_response`（`service.rs:1331-1361`）**直接回填等待中的循环**。若在入站层拦截，会出现「提问永不回填」的死锁（本设计已识别的 V12 风险）。

另两条约束：

- **守卫必须排在斜杠命令解析之前**（`service.rs:636`）——否则 `/init` 之类会在生成期被执行。
- **被拒时不得改写任何状态**（无副作用），只回一条错误消息。

### 5.6 错误码与文案规范

- **码**：`SessionBusy`（新码；proto 的 `code` 为字符串，且其注释已把 `SessionBusy` 列为预期码，见 `visp.proto:309-310`，线级兼容）。
- **文案**：中文「正在生成，请稍候」；英文 “Session is busy: generation in progress, please wait”。
- **禁止**：文案中出现 `cancelled`（大小写不敏感）；不得使用码 `Operation cancelled`。理由：ACP 侧据 `code == "Operation cancelled"` **或** message 含 `"cancelled"` 判定「用户取消」，误判会把忙拒绝显示成一次主动取消。
- **语义区分**：`SessionBusy` = 会话正忙（存在在途循环）；`SessionNotActive` = 非主会话 / 未知会话 / 不可用（保持现状）。
- **客户端表现**：TUI 对 `SessionNotActive` 有专属文案、对 `SessionBusy` 无专属文案，会直接显示 daemon 的 message，并把该 tab 状态置 Error（`crates/visp-tui/src/app.rs:1931-1933`）；ACP 会把该 Error 映射为错误文本 + `Refusal` 终态（`crates/visp-acp/src/translate.rs:130-142`）。
- **状态不可回退（既有行为，故 `SessionBusy` 需特判）**：TUI 收到任意 Error 会把该 tab 置 `Error`，而后续 `Done` **只在状态为 `Running` 时**才改为 `Done`——若不加处理，取消/重连窗口内的忙拒绝会把**正在正常流式**的 tab 永久置 `Error`。故本期在 TUI 对 `SessionBusy` **特判**（不置 `Error`、改一行 Status 提示，仿既有 `SessionNotActive` 特判）；**输入门禁不改**（§12.2）。注：相关站点共**三处**——`route_frame` 的两处相似状态更新块，以及 `render_pending` 的 Error 臂（后者除置状态外，还会 `flush_streaming()` 丢掉正在流式的消息、并 `stop_generating()` 当场放开输入门禁）。三处必须一致，否则「特判」形同虚设；用例须断言「状态不变 + 不 flush + 不提前 stop_generating」。

## 6. 问题二：方案对比与推荐（拒绝式）

### 6.1 方案定调

**核心不变式（本期唯一目标）**：同一会话任意时刻至多一个在途 agent loop。

- **主方案：拒绝式（G1–G3 必做，G4 可选纵深）**。在受理路径上拒绝，而不是重置状态。理由见 §6.3。
- **备选（记录备查，不实施）：取代式**。见 §6.4。

### 6.2 拒绝式方案条目

- **G1（daemon，必做）——受理守卫**
  - 在用户输入分支内、**斜杠命令解析之前**判定：若该会话**存在在途循环的取消令牌**，则**不修改任何状态**，直接向客户端返回一条明确的「会话忙」错误。
  - 判据为**在途令牌**（需新增一个最小查询接口，见 §7 与 §12.4），**不得**用会话 `status` 字段。
  - 保留现有「非主会话（有父会话）一律拒绝」语义不变。

- **G2（判据，必做）——以在途令牌为准，而非 `status`**
  - `status` 是会被多处独立写入的**展示字段**，已证明会与真实循环失步。若守卫只看 `status`，一旦出现「残留 `Running` 但无活循环」，会话会**永久拒绝输入**（只能重启 daemon）。
  - 以在途令牌为判据天然免疫此类失步，并顺带覆盖其反向失步（有活循环但状态非 `Running`）。
  - **精确表述（重要）**：免疫的是**守卫本身**；启动循环既有的「必须 `Idle`」状态闸仍是第二道门，它依旧与 `status` 耦合（见 §8 风险表第 2 条）。

- **G3（去旁路，必做）——移除会绕过 G1 的静默重置**
  - **daemon 侧**：`service.rs:617-631` 的「`Running` 则静默重置为 `Idle`」替换为拒绝逻辑（返回 G1 的忙错误），不再改写状态。
  - **orchestrator 侧**：`orchestrator.rs:386-398` 的非 `Idle` 重置**窄化**为「仅终态（`Completed` / `Error`）→ `Idle`」；**`Running` 不再重置**。
    - ⚠️ **不可整段删除，但理由须订正**（审核修正）：正常收尾时循环内先把状态置为 `Completed`（`agent_loop.rs:912`），随后 orchestrator 的 `handle_done` 又把它置回 `Idle`（两者存在竞态窗口），因此**正常回合结束后最终是 `Idle`**。该重置真正承担的是 **`Error` 终态 → `Idle` 的恢复**，以及上述竞态窗口的兜底。删除它会使**错误/取消后的会话无法再次输入**；「窄化到仅终态→`Idle`」才是既必要又充分的做法。
  - **附带要求（必做）**：`orchestrator.rs:540-543` 在启动循环因忙失败时，当前**只记日志并静默返回**；必须改为向客户端发出与 G1 同语义的「会话忙」错误，否则「静默双循环」会退化为**静默丢弃**（已核实该静默返回确实存在）。
  - **附带处置（必做，审核新发现）**：启动循环前的准备工作**先于** `start_loop` 执行，且失败时**不回滚**——`append_system_prompt_template`（`orchestrator.rs:476/491`）与 `active_agents.register`（`505`）都发生在 `start_loop`（`533`）之前，忙失败在 `541` 直接 `return`。后果：**残留过期 registration** 并**累积 prompt 模板**（在取消窗口内反复提交会叠加）。处置：**选定把二者后移到 `start_loop` 成功之后**（`append_system_prompt_template` 只有追加、无撤销 API，故不取「回滚」方案，避免新增 API）；并补断言。
  - **保留项**：daemon 进程启动时对 DB 中孤儿 `Running` 的恢复性重置（`main.rs:408-420`）**保留**——它作用于**无活循环**的恢复场景，不属于旁路，不受守卫约束。

- **G4（ACP，可选纵深）——终态确认 + 兜底取消**
  - 仅在确认 daemon 终态后才结束本轮；兜底超时补发取消（`agent.rs:212-228`）。**只影响 ACP，不解决 daemon 侧并发**。可作为独立小改动，不阻塞 G1–G3。

- **不需要完整的世代机制，但需要一句「收尾归属判据」G5（三轮审核修正）**
  - 原结论「二阶故障不可能发生」**过强**：正常完成路径存在时序窗口（§5.2 的 B6）——旧回合的收尾会在新回合起来之后执行，踩掉新循环的令牌与状态。
  - **G5（最小归属判据，必做）**：收尾动作（`handle_done` / `handle_agent_error`）在写入终态前**先校验会话当前状态是否仍为本回合写下的那个终态**（`Completed` / `Error`）；若已被新回合改写为 `Running`，则本次收尾为**幂等空操作**（不移除令牌、不改状态）。
  - 这**不是**完整的世代（epoch）+ 全路径归属校验：不需要贯穿循环上下文的世代标识，只需一句「状态未被他人改写」的前置检查；**也不需要**「启动即取代」。
  - **前置条件（须一并写入）**：以上成立的前提是**所有旁路都被堵住**——G3 的两处静默重置已处理、daemon 恢复性重置确认只作用于无活循环、启动循环的忙失败不再被静默吞掉。
  - **设计约束**：任何未来新增的「非 `Idle` 即重置状态后启动」的旁路，都会重新引入本类故障；此类改动必须先回来重新评估 G5 是否仍充分。

- **附带收益（写入）**
  - 令牌不再被旁路静默移除，因此取消动作始终有效：原本「LLM 提问等待无超时且取消无效」会永久卡死的场景，现在用户主动取消即可恢复（取消路径会发 `Error{Cancelled}` 并收尾为 `Error`，`agent_loop.rs:1862-1881`）。

### 6.3 为什么拒绝式使二阶机制整体消失

- 取代式需要回答「旧循环的收尾归属于谁」，于是引入世代 + 归属校验 + 取消/启动时序；拒绝式把问题消灭在「不产生并发」这一步，**没有第二个循环，就没有归属问题**。
- 拒绝式对用户可见的代价：**用户必须等旧循环收尾完成后才能提交下一条**（取代式则无此等待）。该代价已被用户接受（见 §12.2）。
- 注意一个由现有实现带来的窗口：取消动作（`session.rs:460-464`）在取消时**立即移除**令牌，而状态仍是 `Running`（旧循环尚未收尾）。因此「取消后立即重提」在旧循环收尾前会：① daemon 守卫因令牌已移除而**放行**；② 进入 orchestrator 后因状态仍 `Running`、且 G3 已禁止 `Running` 重置，被启动循环的状态闸以 `SessionBusy` 拒绝。**净效果仍是拒绝**（符合拒绝式），但错误来源是第二道门而非守卫，且提示可能短暂反复，直到旧循环收敛。此窗口是否有界、以及是否应调整取消动作的移除时机，列为待定项（§12.4）。

### 6.4 备选方案（记录备查，不实施）：取代式

- **做法**：启动时若该会话仍有在途令牌，先取消旧令牌、再立即装入新令牌；把「重启」显式表达为「取消旧 + 启动新」。
- **优点**：用户无需先取消、无错误噪音（契合用户已按过 Ctrl+C 的意图）。
- **代价**：需要取消/启动的时序设计（先取消后启动、旧循环仍可能在收尾前发帧），并需世代 / 归属校验来防止旧循环迟到收尾破坏新循环——即 §6.3 所述的一整套二阶机制。
- **定位**：不实施，作为对比保留。若未来交互上确实无法接受「先取消再等」，再回到此选项重新评估。

### 6.5 死锁 / 队头阻塞 / 幂等性评估

- **队头阻塞**：拒绝式**不引入任何 join 等待**，被拒即返回，不会因旧循环卡住而阻塞新输入。优于「先取消再等待」。
- **幂等性**：守卫只读令牌、无副作用，重复拒绝无累积影响。
- **死锁**：唯一死锁风险在「把守卫加错层」——必须在用户输入分支内、不得加在入站层（§5.5 的 V12 约束）；且必须排在斜杠解析之前。
- **残留竞态**：守卫判定与 orchestrator 登记令牌之间存在一个**有界**窗口（见 §8 风险表第 3 条），由状态闸兜底，最多产生一条忙拒绝，**不产生第二个循环**。
- **崩溃恢复**：`main.rs:408-420` 的孤儿 `Running` 重置走独立语义，不受守卫与令牌判据影响。

## 10. 测试策略（TDD 分层）

仅描述断言目标与层级，不含测试代码。遵循红 → 绿 → 测试 → 类型检查 → 重构 → 提交。

### 10.1 问题一

- **单元（core 流收集）**
  - 连续同块快照 → 只发增量，且增量拼接恒等于最终全文。
  - 非前缀快照（新块/新一轮）→ 首发该帧全文并重置基线。
  - 文本未变的终帧 → 不发射（空增量）。
- **单元（daemon 映射）**
  - 思考增量事件 → proto 思考块帧，其 `thinking` 即增量文本、`signature` 为空。
- **单元（tui）**
  - 同一思考消息的多次到达为**追加**而非覆盖；子 agent 路由路径同样追加；追加后行内为全文，速率估算仍正确。
- **集成（core 装配 / 回传）**
  - 一轮含思考的响应：对外增量序列拼接 == 完整文本；同时落库的 `extra_blocks` 仍为**完整块**（正文路径含签名）。
- **集成（daemon gRPC 端到端）**
  - Chat 流中思考帧总字节为 O(n) 而非 O(n²)；以「帧数=增量数」与「拼接=全文」表达。
- **端到端（ACP 适配）**
  - 增量帧经 ACP 追加到**同一 `messageId`**；断言最终思考文本**无重复**。
- **回归**
  - `openai_tests` 快照断言**保持不变**（provider 契约未动）。
  - `app_tests` 中断言「覆盖」的用例改写为断言「追加」。

### 10.2 问题二

- **单元（core session）**
  - 存在在途令牌时，查询接口返回「有在途」；无令牌时返回「无在途」；取消后行为符合定义。
  - 断言收尾动作仍为「移除但不取消」（语义未变，已无害）。

- **单元（orchestrator）**
  - 终态（`Completed` / `Error`）→ `Idle` 后第二回合成功启动。
  - `Running`（有在途）→ **不重置状态**、不启动、不发射生命周期 hook。
  - 启动循环因忙失败 → **向客户端发出忙错误**（不得静默返回）。

- **集成（daemon，核心）**
  - 正常流式期间再次提交输入 → 返回忙错误（新码）、**会话状态与令牌均不变**、旧循环继续运行、最终只有唯一的终态。
  - 断言不存在第二个循环、不存在「不可取消的孤儿」、无交错重复回合。

- **集成（答复路径防死锁）**
  - 在输入被拒的时段内，工具审批 / LLM 提问的答复仍能按 `query_id` 回填等待中的循环（回归 V12）。

- **集成（命令顺序）**
  - 生成期提交 `/init`、`/init-agent` → 被守卫拦下（不转发、不产生文件副作用）。

- **集成（恢复路径）**
  - 进程启动时对 DB 中孤儿 `Running` 走强制重置，重置后可正常接受输入。

- **回归改写**
  - `service.rs:3699` 断言由「重置并接受」改为「拒绝（忙）且状态/令牌不变」。
  - `orchestrator_tests.rs:3253 / 3262` 的「同会话第二回合」应**仍然通过**（走终态→`Idle` 合法路径）；新增「`Running` 不重置」用例。

- **触发条件矩阵的分层覆盖（审核后修订）**
  - TUI 窗口（B1a/B1b/B1c 取消、B4 重连）的**存在性**在 **TUI 单元层**断言（取消/重连后输入门禁确实放开）。
  - 核心不变式（在途循环时收到用户输入 → 忙拒绝，状态与令牌不变、无第二个循环）在 **daemon 集成层**注入用户输入断言。
  - **端到端仅保留 ACP 兜底一条**（B2/B3：适配层结束后 daemon 循环仍在跑 → 下次输入被拒），用 ACP 既有脚本化夹具。
  - **不要求**把三个 TUI 按键窗口做成端到端用例：驱动成本高、易 flaky，且窗口本身不是缺陷位置。

## 11. 可发布性与实施顺序

### 11.1 独立可发布性

- **问题二**只影响会话循环所有权与受理逻辑，不改变显示内容语义。
- **问题一**只影响显示域（思考流的追加/覆盖语义），不改变会话状态机与持久化语义。
- 二者代码重叠限于 `visp-daemon::service` 的不同函数区域与 `visp-core` 的不同模块，**无相互依赖**，可各自独立发布、独立回滚；但**回滚的最小原子单位是「按问题整批」**——问题一内部（core 增量变体 + daemon 映射 + TUI 消费）必须同批撤回，否则 `visp-daemon` 编译失败。

### 11.2 建议顺序与依赖

1. **先问题二（拒绝式）**。理由：它是状态正确性问题（孤儿循环、交错回合、状态错乱），风险与用户影响更高；且双循环存在时会叠加「两个循环同时发思考帧」，先消除之可让问题一的验证更干净。落地顺序：
   1. `visp-core::session` 新增「在途令牌存在性」最小查询接口（只读）。
   2. `visp-daemon::service`：用户输入分支加守卫 + 忙错误（新码 `SessionBusy`）+ 移除 `Running` 静默重置（守卫排在斜杠解析之前）。
   3. `visp-agent::orchestrator`：非 `Idle` 重置窄化为「仅终态→`Idle`」；忙失败改为向客户端发忙错误，**并回滚准备工作**（registration 与 prompt 模板追加，`orchestrator.rs:476/491/505`）。
   4. （可选纵深）`visp-acp::agent`：终态确认 + 兜底取消（G4）。
2. **再问题一（B3，不带语义标记）**，按 §4 的模块职责与 §10.1 的断言目标推进。**注意原子性**：新增 `AgentEvent` 增量变体会使 daemon 的穷尽匹配 `agent_event_to_server_message`（无 `_` 兜底）编译失败，故「core 产出增量」与「daemon 映射」**必须同批提交**。
3. §9 的另立项按实测与排期跟进。

## 12. 未决问题（需用户拍板）

### 12.1 proto 语义是否显式标记（已决议：不加标记）

**决议：不加标记**。`ThinkingBlock.thinking` 的语义直接改为「增量」，仅在 proto 注释中写明（见 §3.5、§4.3）。

理由与代价已记录于 §3.5：生产者与消费方同仓同批发布，无跨版本协商需求，新增标记字段的机制成本高于其「契约自描述」收益。已接受的代价：静默语义变更、消费方无法程序化检测版本错配、以及**混合版本本地部署时**旧客户端静默降级（旧 TUI 只显示最后一片）；常规同批发布拓扑下该代价近乎不出现。缓解：proto 注释（并指向语义契约回归测试）+ 发布说明；若未来出现跨版本消费方或第三种语义需求，再评估引入标记。

### 12.2 双 loop 修复是否要改 TUI 门禁（已确认）

**门禁本期不改（用户已确认）**：现有封锁在推理期有效，仅在「取消 / 重连」窗口内会提前放开（B1a/B1b/B1c/B4）；不引入 cancelling 态。

**但新增一处 TUI 错误码特判（用户已批准，反思审核新增）**：忙拒绝会映射为 `Error` 帧，而 TUI 的 `Error` 分支会把该 tab **永久**置 `Error`（后续 `Done` 只在状态为 `Running` 时才改回）——若不处理，取消/重连窗口内的重提会让**正在正常流式**的 tab 显示错误。故对 `SessionBusy` 特判：不置 `Error`，改为一行 Status 提示（仿既有 `SessionNotActive` 特判）。**特判须覆盖三处**（`route_frame` 两处 + `render_pending` 的 Error 臂，后者还含 flush 与 stop_generating 两个副作用）。这与「改门禁」是两件不同的事。

### 12.3 设计文档与代码不一致（建议单独同步）

`docs/design/visp-design-acp.md` 仍把「LLM 提问等待中取消无收尾信号」列为 V10 例外，但 `agent_loop.rs:1862-1881` 已补发 `Error{Cancelled}` + 收尾为 `Error`，§13.10 的方案 A 已落地。该文档中的 V10/V11、§6.6、§13.10、§13 风险表等相关条目已过时。**建议单独立一项「文档同步」**，不在本次两项修复的代码范围内。
